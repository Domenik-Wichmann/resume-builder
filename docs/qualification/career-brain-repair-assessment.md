# Career Brain repair and requalification assessment

## Verdict

**NOT YET QUALIFIED.** Application-controlled identity is markedly stronger and the packet prototype safely handles the sampled unsupported questions. The complete path still has an audited preference-to-implementation overstatement, unstable claim inventories/diffs, positive-answer abstentions and one overbroad leadership phrase. The evidence does not justify a production ingest rollout.

The historical [assessment](career-brain-assessment.md), [results](career-brain-results.md), corpus and baseline are preserved. New experiments are isolated under [revision 2](../../experiments/career-brain/v2/README.md). No application source or migration was changed.

## Final ingest architecture

**Selected production flow remains the existing flow:** authenticated owner source ? one Luna Pro extraction ? exact primary-quote verification ? existing diff/review ? optimistic atomic owner apply ? explicit publication ? Cohere indexing. Its current extractor requests 12,000 output tokens and a 55-second timeout. The new staged architecture is not deployed.

The experimental candidate is: full-source Luna Pro extraction with typed, kind-specific native schema ? application identity reconciliation ? exact multi-span grounding ? independent entailment audit ? conditional missing-entity coverage audit ? deterministic structured/factual comparison with bounded equivalence adjudication ? owner review. Later audits use batches of at most 12 records and exact expected verdict counts. Changed facts in an omitted existing entity require REVIEW, not automatic archival. A fallible map remains optional; controlled results do not support making it mandatory.

Aliases and claims are experimental metadata in the existing transaction's `accepted_changes`; there are no new production claim columns. The application stamps source UUIDs and computes UTF-16 offsets. Audits and extraction cannot assign durable UUIDs. Production integration would still need a reviewable staged request flow, validated provenance persistence and publication controls for evidence excerpts; extending one HTTP call is insufficient.

## Output boundaries and source position

The 145-project source returned all 145 projects plus SQL in one output, and all 145 across five rich chunks. Early, middle and late named-project coverage is complete on this synthetic layout. Raw staged output has 151 rows, including five duplicate SQL records and one supported optional checking skill.

A labeled deterministic replay consolidates exact named skills to 147 records and recomputes offsets against the full original source. All **617/617** resulting spans validate. Raw chunk-local offsets validate 0/617 against the full source; non-null offsets were not mistakenly reported as valid global offsets. Projects are not merged by generic paragraph similarity.

The forced 128-token request returned `finish_reason=length` and null content; validation rejected it and applied no partial candidates. The provider reported 388 completion tokens, so requested limits and reported usage are distinct observations. The ordinary single output completed with `stop`; it was not a truncation failure.

The staged boundary uses explicit project paragraphs and was not separately entailment-audited. Its richer schema differs from the one-output schema. Neither this simple layout nor one large narrative establishes a production strategy for arbitrary careers.
